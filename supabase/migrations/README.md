# Migrations

Forward-only. **A migration that has run in CI is never edited** — a correction
is a new migration. `pnpm supabase db reset` is the single definition of the
schema and runs in CI on every PR.

## Naming

Keep the Supabase CLI timestamp format (`YYYYMMDDHHMMSS_name.sql`), generated by
`pnpm supabase migration new <name>`. `plan-implementacion-codigo.md` refers to
migrations as `0001_roles`, `0002_extensions`, … — treat those as nicknames;
lexical ordering holds under either scheme.

| Nickname | File | Phase |
| --- | --- | --- |
| 0001 roles | `20260902120000_roles.sql` | F0-02 |
| 0002 extensions | _pending_ | F1-01 |
| 0003 tenancy | _pending_ | F1-01 |
| … | … | … |

## History note

The repo's initial commit contained a throwaway prototype migration
(`20260902171408_init_schema.sql`: a 2-table `events`/`tickets` schema with an
opaque-UUID `redeem_ticket`). It was removed during F0-02 — the plan's model
(signed tokens, ~20 tables, RLS, hash-chained audit) is a different system, and
the prototype had only ever run locally, never in CI.

## Canonical audit-row serialization

**Reserved for F1-04.** The byte-exact serialization used for the `scans` hash
chain must be written here and frozen before the first hash is computed. Changing
it later invalidates the entire historical chain.
